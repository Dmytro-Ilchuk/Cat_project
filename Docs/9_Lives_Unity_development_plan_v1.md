# 9 Lives — план розробки в Unity

Версія 1.1 · 21 вересня 2026 · від порожнього проєкту до фінальної збірки

Дизайн-основа: 9_Lives_design_plan_v1_2.md. Документ описує план розробки; виконане позначаємо в чеклістах. Команда: двоє студентів із невеликим досвідом Unity. Орієнтовний строк — три місяці. Основну частину коду й технічних перевірок готує ШІ; студенти ведуть візуал, постановку задач, підключення ресурсів і приймання результатів. Графіка створюється командою, за допомогою ШІ та з ресурсів маркетплейсів.

Календар нижче — 12 тижнів із резервом усередині цього строку. Windows x64 — запропонована перша платформа. Години на тиждень поки не визначені, тому календар контролюємо за готовими збірками та вчасно скорочуємо контент, якщо контрольні точки зриваються.

## 1. Що має бути у фінальній грі

Один кіт має до дев’яти окремих забігів. Смерть завершує забіг і забирає одне життя. Випадкові дари та корм скидаються, а куплені посилення і Спогади зберігаються протягом циклу цього кота. Після дев’ятої смерті новий кіт починає з базовою силою; відкриті предмети, записи та косметика залишаються. Перемога над фінальним босом завершує цикл достроково.

Цільова перша версія:

- Один район, один герой із рухом, стрибком, кігтями, ривком і шипінням.
- Три архетипи ворогів, одна проста елітна модифікація, один бос.
- Вісім бойових макетів, чотири службові кімнати та невеликий прихисток.
- Дванадцять дарів, вісім із них доступні спочатку; шість посилень поточного кота та чотири відкриття дарів для профілю.
- Короткий маршрут із нагородами, необов’язковим випробуванням, розвилкою й магазином.
- Меню, навчання, пауза, результати забігу й циклу, налаштування та продовження гри.
- Збірка, яка запускається на іншому Windows-комп’ютері без Unity Editor.

Тривалість успішного забігу 12–18 хвилин — гіпотеза для тестів. Дев’ять життів не означають дев’ять обов’язкових повних проходжень. Точні параметри беремо з дизайн-плану як початкові значення та змінюємо за результатами гри.

## 2. Технології та перше налаштування

Погоджена версія проєкту — **Unity 6000.6.1f1**, однакова для всієї команди. Залишаємо встановлену версію, у якій уже створений проєкт; попередню пропозицію переходу на 6.3 LTS скасовано. Версія зафіксована в ProjectSettings/ProjectVersion.txt і README. До здачі змінюємо редактор лише за конкретної потреби. Початкова Windows x64 збірка використовує Mono.

Створюємо проєкт із шаблону Universal 2D, з URP і 2D Renderer. У встановленій версії Hub перевіряємо саме 2D-рендерер, а не лише назву шаблону. Unity описує URP, Tilemap, Pixel Perfect і засоби роботи зі спрайтами у своєму [посібнику для 2D](https://docs.unity3d.com/6000.3/Documentation/Manual/setup-project-2d-game.html).

| Частина | Рішення для проєкту |
| --- | --- |
| Керування | Input System із окремими наборами Gameplay та UI; спочатку клавіатура, потім геймпад. |
| Фізика | Rigidbody2D і Collider2D; переміщення фізичного тіла узгоджене з фізичним циклом. |
| Кімнати | Grid, Tilemap, колізії та prefab кімнати з визначеними точками входу й появи ворогів. |
| Камера | Проста камера з межами кімнати; Pixel Perfect. Cinemachine додаємо, лише якщо потрібні його можливості. |
| Інтерфейс | Canvas, TextMeshPro, один EventSystem із модулем нового Input System. |
| Конфігурації | ScriptableObject для параметрів ворогів, дарів, кімнат і покращень. |
| Збереження | Версійований JSON зі станом профілю, циклу та забігу; локальний файл. |
| Перевірки | Unity Test Framework для правил прогресу, нагород і збереження; ручні тести відчуття бою. |
| Командна робота | Git, невеликі гілки задач, однакова версія редактора й пакетів. |
| Збірка | Windows x64, окремі Build Profiles для Development і Release. |

Версії пакетів фіксуємо у Packages/manifest.json та Packages/packages-lock.json. У поточному проєкті вже встановлені URP 17.6.0, Input System 1.20.0, uGUI 2.6.0 та Test Framework 1.8.0. Посилання на документацію 6000.3 нижче залишені як довідкові; поведінку перевіряємо в погодженій версії 6000.6.1f1.

Для старту не потрібні мережеві сервіси, мультиплеєр, Addressables, ECS чи складна система впровадження залежностей. Архітектуру розширюємо, коли з’явиться конкретна потреба.

## 3. Структура проєкту та відповідальність систем

Запропоновані папки всередині майбутнього Unity-проєкту:

```text
Assets/
  _Game/
    Scenes/        Bootstrap, MainMenu, Shelter, Run
    Scripts/
      Core/        запуск і переходи між станами гри
      Player/      керування, рух, атака, здібності
      Combat/      шкода, HP, ефекти
      Enemies/     поведінка ворогів і боса
      Rooms/       маршрут, завантаження кімнат, нагороди
      Progression/ цикл кота, посилення та відкриття
      Save/        дані збереження, читання й запис
      UI/          екрани та відображення даних
      Audio/       музика, звуки, гучність
    Data/          конфігурації контенту
    Prefabs/       герой, вороги, кімнати, UI
    Art/           персонажі, тайли, ефекти, іконки
    Audio/
    Settings/      Input Actions, URP, профілі збірки
    Tests/         окремі тестові збірки коду
    Dev/           тестові сцени та інструменти розробника
  ThirdParty/
Docs/
```

Назви в дереві — майбутня структура, а не вже створені файли. Папки тестів і Dev не мають автоматично потрапляти у фінальну гру через посилання на їхні ресурси.

Чотири основні сцени:

- Bootstrap запускає сервіси, читає збереження та переходить у меню. Вона перша в списку сцен збірки.
- MainMenu дає продовжити, почати новий цикл або змінити налаштування.
- Shelter містить підготовку між забігами та купівлю посилень.
- Run завантажує по одному prefab кімнати; вона не дублюється для кожного макета.

Пауза, вибір дару й результати — екрани інтерфейсу поверх поточної сцени. Для швидкої розробки окремі тестові сцени можуть запускати потрібне оточення, але перевірка релізу завжди починається з Bootstrap.

| Система | Відповідає за | Не повинна самостійно змінювати |
| --- | --- | --- |
| PlayerController та PlayerCombat | Рух, дію, отримання шкоди, подію смерті. | Кількість життів і збереження профілю. |
| RunController | Поточний забіг, кімнати, тимчасовий набір і єдиний підсумок спроби. | Відкриття без перевірки умов. |
| CycleController | Життя кота, Спогади, куплені посилення, завершення циклу. | Дані конфігурацій предметів. |
| ProfileProgress | Відкриті ідентифікатори предметів, записи, косметику. | HP поточного кота. |
| RoomController і RewardService | Бойові цілі, відкриття виходу та одноразову видачу нагороди. | Повторно списувати життя після події смерті. |
| SaveService | Запис і відновлення узгодженого стану гри. | Визначати, хто виграв бій. |
| UI | Відображення й запити дій гравця. | Напряму редагувати лічильники замість правил гри. |

Усі назви орієнтовні; це межі відповідальності, а не вимога створити велику кількість менеджерів. Bootstrap створює один набір довгоживучих сервісів. Перехід між сценами не повинен породжувати другий CycleController або повторні підписки на смерть.

ScriptableObject містить початковий опис дару чи ворога. Життя, поточне HP і придбані покращення зберігаються в окремих об’єктах стану. Конфігурації не використовуємо як файл прогресу користувача. [ScriptableObject](https://docs.unity3d.com/6000.3/Documentation/Manual/class-ScriptableObject.html).

## 4. Календар на три місяці та залежності

Працюємо до конкретного результату кожного тижня. Для цієї команди основна невизначеність — швидкість підключення й перевірки систем у Unity та виробництва узгодженої графіки. ШІ може швидко підготувати код, але кожна можливість усе одно проходить імпорт, налаштування та перевірку в грі.

| Тиждень | Код і механіки за допомогою ШІ | Робота команди | Результат тижня |
| --- | --- | --- | --- |
| 1 | Старт проєкту, ввід, рух, камера, перша збірка. | Установки, репозиторій, освоєння prefab та Inspector, вибір масштабу й палітри. | Кіт або його тимчасовий силует рухається у Windows-збірці. |
| 2 | Бій зі щуром, HP, ривок, шипіння, каркас циклу 9 → 0. | Перевірка керування, перші анімації, читабельність замахів. | Бойовий прототип; смерть завершує спробу й коректно зменшує життя. |
| 3 | 3–4 кімнати, маршрут, вибір дарів, перші шість ефектів. | Макети кімнат, вибір і перевірка набору тайлів, іконки-заглушки. | Короткий забіг із помітно різними наборами здібностей. |
| 4 | Посилення кота, відкриття профілю, магазин, базове збереження й продовження. | Перевірка описів, UI-макети, тест різних рівнів скидання прогресу. | Прокачка між спробами та правильний старт нового кота. |
| 5 | Простий бос, завершення гри, усунення проблем збереження, мінімальне навчання. | Зібрати одну кімнату близько до фінального вигляду, провести повний тест збірки. | v0.5: завершена коротка гра від меню до нового кота або перемоги. |
| 6 | Виправлення за першим зовнішнім тестом; резерв для незавершеного ядра. | Дати збірку 3–5 людям, записати проблеми, остаточно затвердити візуальний стиль. | Рішення про обсяг: повний студентський або скорочений. |
| 7 | Другий і третій вороги, простий елітний варіант, розширення боса. | Фінальні спрайти героя й ворогів, перші готові кімнати. | Усі базові противники працюють. |
| 8 | Повний пул дарів, маршрут і контент, налаштування даних. | Завершення кімнат, іконок, прихистку та потрібних анімацій. | v0.6: увесь погоджений контент у грі. |
| 9 | Завершення UI, геймпада, звуку й налаштувань; перевірка інтеграції. | Тексти, навчання, фінальні звуки, візуальна перевірка всіх екранів. | v0.7: повна версія; нові можливості й контент більше не додаємо. |
| 10 | Виправлення, баланс, вимірювання швидкодії, тести циклу й збережень. | Другий зовнішній тест, перевірка різних ПК, збір відгуків. | Немає блокування проходження та відомих помилок основного прогресу. |
| 11 | Release-збірка, перевірка чистого запуску й оновлення збереження. | Незалежний тест архіву, README, Credits, матеріали захисту. | v0.9: готовий кандидат на здачу. |
| 12 | Лише потрібні виправлення та повторна перевірка. | Фінальне пакування, резерв, репетиція демонстрації та здача. | v1.0: перевірений архів гри й вихідний проєкт. |

Вказані нижче години — лише грубий орієнтир масштабу традиційної розробки з базовим досвідом Unity, а не прогноз людського часу цієї команди за допомогою ШІ. Не застосовуємо до них вигаданий коефіцієнт прискорення. Після другого тижня оцінюємо фактичний темп: скільки завершених задач команда здатна поставити, підключити та перевірити.

| Етап | Результат | Основна залежність | Людино-години |
| --- | --- | --- | --- |
| 0 | Узгоджений обсяг і список задач. | Дизайн v1.2. | 4–6 |
| 1 | Порожня збірка працює на двох ПК. | 0. | 6–10 |
| 2 | Котом приємно керувати. | 1. | 14–22 |
| 3 | Один завершений бойовий прототип. | 2. | 14–22 |
| 4 | Дев’ять спроб і правильні скидання стану. | 3. | 14–22 |
| 5 | Послідовність кімнат і короткий маршрут. | 3; інтеграція з 4. | 18–28 |
| 6 | Дари, синергії та посилення кота. | 4 і 5. | 16–24 |

| 8 | Весь погоджений ігровий контент. | 7. | 30–46 |
| 9 | Узгоджений піксельний вигляд. | Стиль після 2; завершення після 8. | 24–40 |

Базовий орієнтир суми робіт — 208–324 людино-години, із резервом 20% — приблизно 250–390. Для нашого способу роботи кориснішим показником буде кількість прийнятих задач і готових збірок за тиждень. Генерація файлів сама по собі не означає завершення етапу.

У нашому календарі тижні 10–12 відведено під баланс, перевірки, пакування й резерв. Якщо v0.5 не працює до кінця тижня 6, одразу переходимо на скорочений обсяг із розділу 19. Якщо повний контент не готовий до кінця тижня 8, недороблені додаткові дари й макети переносимо за межі здачі. Час перевірки основного циклу зберігаємо.

У наступних розділах «власник А» або «власник Б» означає людину, відповідальну за постановку задачі та приймання. Основну реалізацію коду для цих задач готує ШІ; відповідальний підключає її в редакторі, запускає перевірки й вирішує, чи виконана задача.

## 12. Етап 7 — збереження та повний короткий цикл

Власник: А; Б перевіряє сценарії перезапуску на іншому ПК.

Три рівні збереження вкладаємо в один узгоджений запис із номером формату:

| Рівень | Мінімальні дані |
| --- | --- |
| Profile | Відкриті ID дарів, записи, косметика, налаштування. |
| Cycle | ID кота/циклу, стан циклу, життя, Спогади, куплені ID покращень. |
| RunCheckpoint | ID забігу, seed і стан випадкових виборів, позиція маршруту, HP, корм, дари, перезарядки, отримані нагороди. |

- [ ] Зберігати у каталозі Application.persistentDataPath; не в Assets і не поруч із виконуваним файлом. Unity надає цей шлях для даних, що мають переживати запуск програми. [Документація шляху збереження](https://docs.unity3d.com/6000.3/Documentation/ScriptReference/Application-persistentDataPath.html).
- [ ] Зберігати прості дані та ID, а не посилання на GameObject; відновлювати ID через каталог конфігурацій.
- [ ] Додати номер формату, перевірку даних, тимчасовий файл та заміну основного після успішного запису; залишати попередню коректну копію.
- [ ] Зберігати старт кімнати й завершені рішення в безпечних точках. Після видачі нагороди одночасно записувати результат і позначку, що її вже отримано.
- [ ] Вихід посеред незавершеного бою повертає на початок цієї кімнати з її початковими ресурсами. Такий повтор дозволений правилами MVP.
- [ ] Смерть однією операцією фіксує новий залишок життів і прибирає активний checkpoint. Продовження не має відновлювати запис перед уже завершеною смертю.
- [ ] Зберігати перемогу, покупки й новий цикл одразу; не покладатися лише на завершення програми.
- [ ] Перевірити чистий профіль, звичайне продовження, неповний/пошкоджений файл і відновлення останньої коректної копії. Нові несумісні формати не читати як старі без перевірки.
- [ ] Додати простого боса-заглушку з однією атакою та під’єднати справжню перемогу.

Готово: коротка гра має меню, прихисток, 3–4 кімнати, дари, боса, смерть, дев’ять спроб, нового кота й продовження після перезапуску. Це перша повна версія циклу, v0.5, придатна для зовнішнього тесту.

Якщо запис не вдався, показуємо помилку збереження та можливість повторити; не повідомляємо, що прогрес збережений. При перевірках збереження використовуємо окремий тестовий профіль, щоб не втратити прогрес реального тестера.

- [ ] Зафіксувати список відомих дрібних обмежень; прибрати блокування проходження, втрату прогресу й помилки життів.

Готово: немає відомих проблем, що блокують старт, прохід, завершення циклу або продовження збереження. Версія v0.9 — кандидат на реліз. Нові механіки після цього етапу не додаємо.

## 17. Етап 12 — фінальний білд і здача

Власник: А готує збірку, Б незалежно її перевіряє.

- [ ] Зафіксувати перевірений стан репозиторію та номер версії 1.0.0.
- [ ] Відкрити File → Build Profiles і вибрати Windows Release-профіль. Власні профілі дозволяють окремо зберігати конфігурації та список сцен. [Build Profiles у Unity 6.3](https://docs.unity3d.com/6000.3/Documentation/Manual/build-profiles.html).
- [ ] Перевірити список сцен: Bootstrap перша, усі потрібні сцени є, тестові сцени не включені.
- [ ] Вимкнути Development Build, Script Debugging, підключення профайлера та розробницькі команди. Перевірити відсутність доступного тестового меню.
- [ ] Використати вже перевірений backend і графічні налаштування; не міняти їх уперше в день здачі.
- [ ] Перевірити назву продукту, іконку, версію й незмінність ідентифікаторів, які впливають на пошук збереження.
- [ ] Зібрати в нову чисту папку та запустити отриманий виконуваний файл.
- [ ] Передати на інший ПК усю папку збірки, включно з .exe, *_Data та створеними Unity бібліотеками; одного .exe недостатньо.
- [ ] На іншому ПК пройти перевірку: чистий старт, один забіг, смерть, покупка, вихід, продовження, перемога або завершення циклу на тестовому профілі.
- [ ] Перевірити пакування збережень: особисті й тестові файли прогресу не вкладаються в архів гри.
- [ ] Додати короткий README українською: запуск, керування, правила дев’яти життів, продовження з межі кімнати, відомі обмеження та перевірений ПК.
- [ ] Додати Credits із авторами й відомостями про використані сторонні ресурси; підготувати запис геймплею та кілька скриншотів для захисту.
- [ ] Створити архів NineLives_Windows_v1.0.0.zip, розпакувати його в іншу папку та ще раз запустити гру.
- [ ] Зберегти фінальний проєкт, README для відкриття в точній версії Unity та позначку версії у Git. Якщо університет просить вихідний проєкт, готувати його окремо від архіву гри.

Готово: переданий архів розпаковується й запускається на іншому ПК без Unity Editor; версія відтворюється з репозиторію; керування й правила зрозумілі з доданого README. Публікація в магазині або на хостингу — окрема задача після локальної здачі, якщо вона потрібна.

Ці перевірки потрібні через ціну помилки в обмеженому циклі життів. Правила стану зручно перевіряти автоматично, відчуття керування та читабельність — вручну.

| Сценарій | Очікуваний результат |
| --- | --- |
| Старт нового циклу | 9 життів, базова сила, відкриття профілю доступні. |
| Перша смерть | 8 життів; тимчасове скинуто; Спогади й посилення кота збережено. |
| Повторна подія смерті того самого забігу | Додаткове життя не списується. |
| Смерть із одним життям | 0, цикл завершено, продовження цього кота недоступне. |
| Новий кіт після поразки | 9 життів, базова сила, нуль Спогадів; відкриття лишаються. |
| Перемога в першій спробі | Цикл завершено успішно; решту спроб проходити не потрібно. |
| Смерть героя й боса в одному кадрі | Лише один визначений підсумок. Робоче правило: при смертельній шкоді герою цього кроку — поразка. |
| Немає грошей або вузол уже куплено | Покупка відхилена, баланс не змінюється. |

| Вихід у бою | Життя збережене; продовження зі старту цієї незавершеної кімнати. |
| Перезапуск після записаної смерті | Прихисток або підсумок циклу, а не відновлений живий герой. |
| Вихід під час вибору дару чи покупки | Узгоджений стан: операція або виконана один раз, або ще не виконана; немає втрати валюти без результату. |
| Пошкоджений файл | Контрольоване повідомлення й коректна резервна копія за наявності; гра не зависає. |

## 19. Командна робота і скорочення обсягу

Пропонований розподіл: А — технічний інтегратор і менеджер задач для ШІ; Б — відповідальний за візуал, кімнати та наповнення. А стежить за основною збіркою, отримує й перевіряє код, підключає компоненти, передає відтворювані помилки. Б працює з графікою, маркетплейсами, анімаціями, UI та параметрами контенту. Баланс, обсяг і зовнішні тести робите разом. Ці ролі можна міняти; обидва мають уміти зібрати й запустити гру.

ШІ готує скрипти, конфігурації, автоматичні перевірки, пояснення підключення та виправлення за даними помилок. За наявності доступу до робочого Unity-середовища частину перевірок можна автоматизувати. Якщо код лише переглянуто, це не вважаємо підтвердженим запуском у Unity.

Правила роботи:

- Одна задача має одного відповідального за завершення; інший перевіряє результат. Запити до ШІ також прив’язуються до конкретних задач.
- Одну сцену або великий prefab одночасно редагує один учасник. За потреби розбиваємо сцену на незалежні prefab-компоненти.
- Задачі тримаємо малими: одна поведінка або один екран із зрозумілою перевіркою. Орієнтир — завершення за одну робочу сесію, включно з підключенням коду від ШІ.
- Перед об’єднанням змін проєкт компілюється, а короткий тест зачепленої можливості проходить.
- Щотижня або після кожної контрольної точки маємо збірку, яку може запустити інший учасник.
- Сторонні ресурси зберігаємо окремо; походження й потрібні авторські позначки записуємо під час додавання.
- Помилки описуємо через кроки відтворення, очікуваний результат, фактичний результат, версію та seed за потреби.

Якщо повний обсяг не вкладається, погоджуємо скорочену версію: 4 бойові макети, 2 архетипи ворогів, 6 дарів із двома комбінаціями, 3 покращення циклу, простий бос і базове оформлення. Маршрут робимо коротшим без повторів макетів. Переносимо косметику, еліту, частину декору й складні звукові варіації.

Зберігаємо завершення гри, дев’ять спроб, коректні скидання прогресу, хоча б одне відкриття між котами, продовження, зрозуміле керування й перевірку фінального архіву. Кількість контенту можна зменшити; працездатність основного циклу залишається умовою здачі.

## 20. Перші робочі сесії

Перша сесія: обсяг, однакова Unity, репозиторій і порожній проєкт. Найближча контрольна точка етапу 1 — стартова сцена й перша Windows-збірка на двох ПК; якщо налаштування потребуватиме більше однієї сесії, це вкладається в перший тиждень.

Друга сесія: Player prefab, біг, стрибок, камера та одна тестова кімната. Другий учасник перевіряє рух і готує масштаб тайлів та героя.

Наступна контрольна ціль: кіт рухається, б’є одного щура, отримує шкоду й завершує спробу смертю. Після цього підключаємо лічильник циклу та прихисток.

Першою великою демонстрацією має стати v0.5 наприкінці п’ятого тижня: повний короткий цикл на тимчасовій графіці, зі збереженням, кількома дарами та простим босом. Після нього можна обґрунтовано оцінити залишок роботи й темп виробництва контенту.

## 21. Як ставити задачі ШІ й приймати код

Робоча одиниця — маленька можливість, яку можна побачити та перевірити. Наприклад: «додати ривок із однією перезарядкою» або «після смерті зберегти Спогади й зменшити життя один раз». Задача на всю бойову систему одночасно ускладнить пошук причини помилки.

Порядок роботи:

1. Зафіксувати робочий стан у Git та вибрати одну задачу.
2. Надати ШІ актуальні файли, версію Unity, потрібний розділ дизайну й очікувану поведінку.
3. Отримати реалізацію та короткий перелік потрібних дій у редакторі: компоненти, поля Inspector, посилання, шари й налаштування.
4. Відкрити проєкт, дочекатися імпорту й перевірити Console. За помилки передати повний текст, кроки відтворення та очікуваний результат.
5. Виконати критерії приймання в Play Mode, а для контрольної точки — і в окремій збірці.
6. Перевірити, що попередня основна поведінка працює. Прийняти зміну, зберегти її в Git і перейти до наступної задачі.

Шаблон задачі:

```text
Задача: коротка назва однієї можливості.
Контекст: версія Unity, пов’язані сцени, prefab і скрипти.
Правило гри: конкретна очікувана поведінка з дизайн-плану.
Обсяг зміни: що треба реалізувати в цій задачі.
Готово, коли: 3–5 спостережуваних перевірок.
Результат: зміни коду, дії в редакторі, виконані перевірки
та перевірки, що ще потребують запуску людиною.
```

Приклад першої задачі після налаштування: реалізувати горизонтальний рух для існуючого Player prefab через Input System; перевірити рух ліворуч/праворуч, зупинку, зіткнення зі стіною й блокування вводу в паузі. Стрибок і ривок додаються наступними маленькими задачами.

Мінімальні навички, які команді потрібні навіть за активної допомоги ШІ: відкрити сцену, створити й редагувати prefab, додати компонент, призначити поле Inspector, визначити layer, прочитати Console, зробити commit і запустити збірку. Їх освоєння входить у перші два тижні.

## 22. Візуал із власних робіт, ШІ та маркетплейсів

Визначаємо один зразок стилю в перший тиждень: кіт на фрагменті кімнати, масштаб тайлів, обмежена палітра та товщина контуру. До масового виготовлення ресурсів перевіряємо цей зразок у грі з реальною камерою.

- Власні роботи: ключовий силует кота, потрібні анімації, остаточні правки тайлів та читабельності атак.
- ШІ: пошук візуального напрямку, варіанти іконок, фони й заготовки. Кадри для анімації потребують ручної перевірки масштабу, послідовності та позиції опорних точок.
- Маркетплейси: сумісний базовий набір оточення, UI-елементи або звуки, які команда адаптує до спільного стилю.

Для кожного набору перевіряємо розмір тайлів, палітру, контури, потрібні стани анімації та право використання в запланованій збірці; зберігаємо джерело й відомості про автора. Купівлю ресурсів команда вирішує окремо після вибору стилю. Для MVP можна обійтися придатними безкоштовними або власними ресурсами.

Набори, що потребують різних масштабів або різко відрізняються стилем, створюють додаткову роботу з адаптації. Тому один узгоджений набір оточення й один герой важливіші за кількість знайдених ресурсів. Масове оформлення всіх кімнат починаємо після перевірки масштабу на рухомому коті.
